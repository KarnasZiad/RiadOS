```mermaid
  Rel(staff, web, "Utilise", "HTTPS")
  Rel(web, api, "Appelle", "JSON / HTTPS, JWT + cookie httpOnly")
  Rel(api, pg, "Lit et écrit", "SQL, transactions SERIALIZABLE")
  Rel(api, redis, "Verrous et cache", "RESP")
  Rel(api, redis, "Publie des jobs", "BullMQ")
  Rel(worker, redis, "Consomme des jobs", "BullMQ")
  Rel(worker, pg, "Lit et écrit", "SQL")
```

## Niveau 3 — Composants de l'API

L'API est découpée par **bounded context** (DDD). Chaque contexte possède son module NestJS ; la
logique métier pure (objets valeur, calcul de prix) vit dans un dossier `domain/` sans dépendance au
framework, ce qui la rend testable unitairement.

```mermaid
flowchart LR
  subgraph Plateforme
    auth[Auth<br/>JWT, refresh rotation, rôles]
    tenancy[TenantDb<br/>set_config app.tenant_id]
    lock[RedisLock<br/>SET NX PX + Lua]
    health[Health<br/>Postgres, Redis]
  end

  subgraph Booking
    rooms[Rooms]
    reservations[Reservations]
    domain[domain/<br/>StayPeriod, pricing]
  end

  subgraph Billing [Billing — v2]
    invoices[Invoices]
    pdf[PDF worker]
  end

  subgraph Housekeeping [Housekeeping — v2]
    tasks[Tasks]
  end

  reservations --> domain
  reservations --> lock
  reservations --> tenancy
  rooms --> tenancy
  invoices -. événement ReservationCheckedOut .-> reservations
  tasks -. événement ReservationCheckedOut .-> reservations
```

Les contextes Billing et Housekeeping ne dépendent pas directement de Booking : ils réagiront à des
événements de domaine (`ReservationCheckedOut`) publiés dans une file BullMQ.
